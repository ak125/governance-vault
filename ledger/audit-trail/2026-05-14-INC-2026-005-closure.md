## 2. Root cause détaillée (rappel PR #320)

Le bug : tout fichier `frontend/app/routes/pieces*` ou `constructeurs*` qui
exportait :

```ts
export const headers: HeadersFunction = () => ({
  "Cache-Control": "public, max-age=60, s-maxage=86400, stale-while-revalidate=3600",
});
```

… écrasait le `Cache-Control: no-cache` posé par le loader sur ses
`throw new Response(..., { status: 503, headers: { ... } })`. Remix invoque
`headers` pour **toutes** les réponses (succès et erreurs), donc le
`s-maxage=86400` du succès était appliqué aux 5xx.

Cloudflare honorait le `s-maxage` → cachait la 500 pendant 24h. Une seule
RPC froide qui timeoutait à 2s (`RPC_TIMEOUT_MS=2000`, abaissé par PR #93 sans
mesure préalable de `build_vehicle_page_payload` 692ms warm / ~2s cold)
contaminait le cache CDN sur 24h pour cette URL.

PR #320 (Helper `~/utils/cache-control#buildCacheHeaders`) lit `errorHeaders`
en premier, puis `loaderHeaders`, puis fallback `successPolicy`. Plus jamais
de leak success → error.

## 3. Defense-in-depth livrée dans PR-1 (cette closure)

### Tactical anti-récidive — invariants mécaniques

- **AST rule** `.ast-grep/rules/frontend-no-headers-bypass-buildCacheHeaders.yml`
  (severity `error`) : refuse tout `headers: HeadersFunction` qui contient
  `cache-control` mais n'appelle pas `buildCacheHeaders`.
- **AST rule** `.ast-grep/rules/no-test-routes-without-env-guard.yml`
  (severity `error`) : tout fichier `frontend/app/routes/__test.*` doit avoir
  un triple ENV guard (`NODE_ENV`, `ENABLE_TEST_ROUTES`, `READ_ONLY`) pour
  garantir qu'il ne fuit jamais en PROD.
- **Bash lint** `scripts/lint/check-cache-headers-ok-references.sh` : refuse
  les commentaires d'exemption `// CACHE-HEADERS-OK` sans référence
  `(#NNN | INC-YYYY-NNN | ADR-NNN)` + raison. Wiré dans `.husky/pre-commit`
  + step CI `lint`.

### Observabilité runtime

- **Port `notify503ToErrorLog`** dans `frontend/app/utils/pieces-vehicle.loader.server.ts`
  (déjà présent dans `constructeurs.$brand.$model.$type.tsx` via PR #167) avec
  les 2 subjects `LOADER_503_RPC_INVALID_PAYLOAD` + `LOADER_503_BACKEND_RPC_ERROR`.
  Comble le blindspot historique : les `throw new Response(503)` du loader
  pieces n'écrivaient rien dans `__error_logs`.

### CI smoke v2

- **`prod-smoke-tests.yml` extension** : sample 11 → 150 URLs stratifiées,
  seed déterministe `date +%Y%m%d` (rotatif quotidiennement, reproductible
  toute la journée). Script `scripts/ci/sample-smoke-urls.ts` génère les URLs
  + écrit manifest JSON (audit-trail per run, artifact CI 30j).
- Anti-flake `runs:3` aligné pattern PR #504 (perf-gates). Fail si
  `rate_5xx > 0,5 %`.

### Outillage incident

- **`scripts/seo/gsc-5xx-evidence-batch.ts`** (Phase A) : audit empirique
  reproductible, sample 5000 URLs stratifiées, seed persisté dans JSON
  output (`meta.seed`, `meta.source_lists`, `meta.sitemap_revision_hash`,
  `meta.script_git_sha`).
- **`scripts/ops/cloudflare-purge-by-pattern.sh`** (Phase B) : dry-run par
  défaut, `--apply` + `--max-urls=N` obligatoire, `--hostname-wide` interdit
  sauf `--i-understand-impact`, warmup post-purge avec UA identifiable
  `AutoMecanikCacheWarmer/1.0`, pré-flight check `__error_logs`,
  audit-trail JSON par run.

### Test e2e invariant

- **`frontend/tests/e2e/cache-control-on-error.spec.ts`** : valide que les
  URLs 200 portent `s-maxage`, que les 410/404 ne fuient pas `s-maxage=86400`
  (axe CDN qui était la racine du bug).
